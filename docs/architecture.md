## 1. 一句话架构

一个云端多租户后端(FastAPI + PostgreSQL + 对象存储),对上提供两个端:Web 管理端(内部作业:上传、审核、词表、事件)与微信小程序使用端(一线选款:筛选、图墙、选图篮、转发)。所有 AI 打标统一抽象为"任务",打标结果连同完整溯源落库;所有关键业务行为落为只增事件流水。

```text
                     ┌─────────────────────────────┐
   微信小程序使用端 ──┤                             │
   (筛选/图墙/选图篮) │      FastAPI 多租户后端       │──→ PostgreSQL(标签/任务/事件/词表)
                     │  租户中间件 · 任务执行 · 事件  │
   Web 管理端 ───────┤                             │──→ 对象存储(七牛/OSS,原图+缩略图)
   (上传/审核/词表)  │                             │
                     └──────────────┬──────────────┘
                                    │ task_type=tagging
                                    ▼
                          阿里百炼 Qwen-VL-Max(OpenAI 兼容接口)
```

## 2. 系统组成与技术选型

### 2.1 后端:Python + FastAPI

**选型:FastAPI(Python 3.11+)。**

- 旧项目 balloon-tagging-eval 已是 Python 技术栈(providers/score/sync_corrections 等全部 Python),打标提示词、词表切分、schema 兜底逻辑可**整段迁移**,不重写。【降低迁移风险】
- Qwen-VL 与 Gemini 均走 OpenAI 兼容 SDK(`openai` 库),旧项目 `providers.py` 的调用封装(指数退避、token 统计、图片压缩为 data URI)直接复用。【符合:不变量二 — token 用量采集在此层完成】
- FastAPI 的 pydantic 模型天然承载"输出 schema 版本化":每个 task_type 一套 pydantic schema,对应 `schema/output_schema.json` 的迁移物。【符合:不变量四】
- 异步 IO 适合"批量打标 = 大量外部 API 调用"的 IO 密集型负载。

**不选** Django(ORM/admin 过重,admin 反而诱使我们做"租户自助管理界面",违背交付纪律)、不选 Node(团队与旧资产都在 Python)。

### 2.2 数据库:PostgreSQL

**选型:PostgreSQL 15+。** 详细表结构见 [data-model.md](./data-model.md)。

- **JSONB** 承载"按 task_type 各自定义的输出 schema"与溯源明细,既结构化又不为每个未来任务类型改表。【符合:不变量四 — 任务表结构对类型开放】
- 标签维度筛选("红金 且 立柱")靠**规范化标签表 + GIN 索引**,不需要向量库。【符合:隔断墙 — 检索用标签过滤,不做向量检索】
- 行级 `tenant_id` 列 + 应用层强制过滤,后续可平滑升级到 Row-Level Security(RLS)。【符合:不变量一】
- 单实例起步,读写量在数万张图规模下远未触及 PG 上限。

**不选** SQLite(旧项目本地工具用 SQLite 够了,但多租户云端需要并发与 JSONB/GIN)、不选 MongoDB(事件流水与溯源要强一致与事务,关系库更稳)。

### 2.3 对象存储:七牛 vs 阿里云 OSS

**建议:阿里云 OSS。** 理由是"与百炼同厂,少一个账号体系、少一次跨云出网"。对比:

| 维度 | 阿里云 OSS | 七牛云 Kodo |
|---|---|---|
| 与百炼 Qwen-VL 同厂 | ✅ 同为阿里云,内网可达、同一套 RAM 账号与账单 | ❌ 跨云,打标取图需公网/签名 URL |
| 客户既有账号 | 交付方案已要求示例客户自备**阿里云百炼账号**,OSS 顺带开通,账单归口一处 | 需另开七牛账号 |
| 图片处理(缩略图) | 内置图片处理(缩放/格式转换),缩略图墙可用 URL 参数实时生成 | 亦有 dora 图片处理,能力相当 |
| 单租户数据独立部署 | Bucket 按 `{tenant_id}/` 前缀隔离,未来可按租户拆 Bucket / 拆账号 | 同样支持 |
| 价格 | 存储/流量略高,但省去跨云出网费 | 存储/CDN 单价常更低,适合大流量分发 |
| 迁移风险 | SDK 成熟 | SDK 成熟 |

**决策依据:** 本期是"内部选款库",流量小、图片总量 2–3 万张,七牛的 CDN/价格优势用不上;而"与百炼同厂、账单归一、内网取图"对交付和成本核算是实打实的省事。**因此选 OSS。**

> 关键:无论选哪家,**业务层通过 `asset_id` + 内容 hash 访问资产,不出现任何 provider SDK 之外的路径依赖**;存储适配封装成一个 `StorageBackend` 接口(`put/get/presign/thumbnail_url`),换供应商只改这一个实现。【符合:不变量三 — 更换存储供应商业务层零改动】

> **【Q4】缩略图统一口径:** 默认**不预生成、不落库**,由 `StorageBackend.thumbnail_url()` 在取图时以 OSS 图片处理参数**实时生成**(缩放/转 JPEG)。**唯一例外:** 入库时若探测到 OSS 图片处理不支持的源格式(如个别 HEIC 变体、CMYK 等),在入库管线里预生成一张 JPEG 缩略图并作为该 asset 的派生物存储,`asset` 记 `thumb_key`;其余情况 `thumb_key` 为空、走实时。migration §3.3 的"另生成 JPEG 缩略图"据此收敛为"仅不支持格式预生成",不是全量预生成。

### 2.4 打标引擎:阿里百炼 Qwen-VL-Max

**生产配置锁定(迁移自旧项目评测结论,见 [migration.md](./migration.md)):**

```text
model        = qwen-vl-max        # 83 张全量评测 structure 判错率 3.6%,优于 gemini 4.8%,且更快更省
few-shot     = 无                 # 三轮 few-shot 实验判错率反涨到 10.8–13.3%,已关闭
temperature  = 0                  # 确定性输出
image_max_edge = 1568             # 发送前长边压缩,控成本
```

- 调用走 OpenAI 兼容接口(`https://dashscope.aliyuncs.com/compatible-mode/v1`),便于将来换/加模型只改配置。
- 每次调用返回的 `input_tokens / output_tokens / latency` **必须落进溯源记录**。【符合:不变量二】
- Gemini(`gemini-3.x-pro`)配置保留为"能力上限对照",不进生产路径。

### 2.5 部署:单机 Docker Compose

**选型:单机 Docker Compose 起步。**【符合:隔断墙 — 部署编排单机 Docker 起步】

```text
docker-compose:
  api        FastAPI(uvicorn/gunicorn)
  worker     打标 worker(批量任务执行,与 api 同镜像不同入口)
  postgres   PostgreSQL 15 + 持久卷
  # 【队列=PG】不引 Redis:任务队列走 PG 的 SELECT ... FOR UPDATE SKIP LOCKED,少一个依赖(见 §3.3)
  # 对象存储用云端 OSS,不入 compose
```

- 一台云主机即可承载首个租户。多租户是**数据结构层**的事(每行带 tenant_id),不是"每租户一套部署"——不为"未来多机"提前搭 K8s。【符合:留位置不建房间】
- 未来某租户要求数据物理独立时,靠"同一套镜像 + 独立 compose + 独立库/Bucket"复制交付,业务代码零改动。【符合:不变量一、三】

## 3. 关键机制设计

### 3.1 租户隔离贯穿全链路 【符合:不变量一】

- **数据层:** 每张业务表第一列 `tenant_id`,无一例外(公共选款库用保留租户号 `tenant_id = 0` 承载,不用 NULL)。
- **API 层:** 请求经"租户中间件"解析出 `tenant_id`(Web 管理端来自登录会话所属租户;小程序来自绑定租户),注入请求上下文;所有 DB 查询默认拼 `WHERE tenant_id = :ctx_tenant`。
- **存储层:** 对象 key 一律 `{tenant_id}/{asset_id}/{original|thumb}.ext`。
- **日志层:** 结构化业务日志与事件流水均带 tenant_id。
- **跨租户访问**(未来的平台公共库聚合)必须显式声明并落审计事件,不做隐式全表。

> **【裁决九】`platform_session` 使用纪律(跨租户访问口径二分):** 平台侧会话按用途分两类——
> ① **只读基础设施扫描**(如 worker 轮询各租户 pending 任务、健康检查):凭 `reason` 参数显式声明
> 即可、日志留痕,**不落 event**,避免基础设施心跳淹没审计视图;② **数据性跨租户聚合/导出**
> (查询③平台级计量、任何跨租户读业务数据并对外产出的操作):**必须**落 `sensitive=true` 审计事件
> (`tenant_id=0`【N5】),一次调用一条,不得豁免。判据:**触碰租户业务数据并产生对外结果的落事件;
> 只为调度自身服务的只读扫描声明即可;拿不准按第 2 类。** 现有唯一平台侧调用点 `worker:scan_pending`
> 属第 1 类。裁决记录见 [reviews/R03-.../裁决记录_裁决九](../reviews/)。

### 3.2 任务契约:一切 AI 操作皆任务 【符合:不变量四】

统一抽象:`任务(输入资产, task_type, 配置版本) → (结构化输出, 溯源记录)`。

- 本期只实现 `task_type = tagging`。任务表结构对类型开放:`task_type` 是普通字符串列,`asset_id`(输入资产,宪法任务契约的输入即资产)/ `output`(JSONB)/ `config_version` 通用。【Q5:术语统一为 `asset_id`,不再用 `input_ref`】
- 输出 schema 按 task_type 版本化:`tagging` 的 schema 迁移自旧项目 `schema/output_schema.json`(四维:主题/配色/造型/场景 + 衍生字段),以 pydantic 模型 + 版本号 `tagging_output_v2` 落地。
- **不做**插件框架、任务编排引擎、引擎市场。新增任务类型 = 新增一个 `task_type` 常量 + 一套输出 schema + 一个执行函数,核心表不动。【符合:不变量四"禁止"条款】

### 3.3 打标批量执行 + 低置信度复核队列 + 人工修正

- **批量执行:** worker 从任务队列取待打标资产,调 Qwen-VL,写 `tag` 表(每条标签带完整溯源)+ 写 `task` 记录 + 落"打标完成"事件。并发/重试/断点续跑复用旧项目 `run` 配置(concurrency、max_retries 指数退避、resume 跳过已完成)。**【N3】词表版本注入锁定:** worker 注入 prompt 的词表版本取自 `config_version.payload.vocab_versions`,**批次创建时锁定、批次内不变,不读运行时最新版**——避免同一 `run_id` 的标签溯源到不同词表版本,污染查询②的定位。
- **复核队列:** 打标结果 `confidence < 阈值` 或 `needs_review = true` 的进入复核队列(本质是一个按条件筛的视图/查询,不是新子系统)。阈值是租户级配置项,变更落"配置变更"事件。【符合:留位置不建房间 — 队列 = 查询,不建独立引擎】
- **人工修正(三种操作)【C1】:** 审核员在 Web 端对标签有三类操作,**任何一种都不覆盖/不销毁原始值**:
  - **改值(update):** `tag_correction` 追加一行 `kind='update'`,`tag.value` 更新为新概念键,`old_value` 保留;
  - **删错标(remove):** 模型幻觉出的标签(如根本不存在的"拱门"),`tag.status` 置 `removed`,`tag_correction` 追加 `kind='remove'`(`new_value` 空)。检索一律 `status='active'`,该标签退出检索但原始行与溯源永久保留;
  - **补漏标(add):** 模型漏掉的造型,**新增一条 `tag` 行**(`source='human'`,模型溯源列为空),**不走修正链**,只落"人工修正"事件。
  - 三种操作均落 `event`(event_type='correction')。表结构与 CHECK 见 [data-model.md](./data-model.md) §3.5/§3.6。【符合:不变量二 — 人工修正不覆盖原始值】
- **【N1/裁决五】重打收敛(supersede):** 词表升级后的重打批次(见查询②),新旧标签先并存供验收;**人工验收通过后**,系统对同 `(asset_id, dimension)` 且词表版本早于本批的 `active` 标签**批量置 `superseded`**(落 `tag_correction` kind='supersede', source='model' + event)。检索只查 `active`,旧标签退出但原行永久保留——重打不再"双计/旧错值继续命中"。
- **【A-6/裁决五】归一化反查失败落库(unresolved):** 模型词形在 `alias_map` 与当期 `vocabulary.labels.zh` 都查不到时,**照常写 `tag`**:`value` 存**裸原词形**(不加 `raw:` 前缀——concept_key 强制 ASCII,中文词形天然不冒充概念键,隔离靠状态列而非字符串魔法)、`status='unresolved'`、`needs_review=true`,进复核队列。**闭环强制:** 人工归类(补 alias/扩词表)后走修正链转正——`kind='update'`(old=原词形, new=concept_key)+ status 迁回 `active`;判为垃圾则 `kind='remove'`。unresolved 不允许无限期滞留,复核队列视图默认包含它。(否决"整条拒收"方案:会丢同图其他维度可用标签,与"多造型都要列出"相悖。)
- **【Q1/裁决二】颜色检索默认按主色:** `dimension='color'` 的标签带 `role`('primary'|'accent',**必选**)。消费者挑气球方案按主色调判断,故颜色筛选**默认只命中 `role='primary'`**(搜"红金" = 主色含 red 与 gold);另提供"含点缀色"开关,放宽到全部 color 标签。`scheme_name`(整套配色命名,如"红金")落**独立维度 `color_scheme`**、自由文本,不混入 color 维,避免污染单色统计与筛选。

> **【队列=PG】** 任务/复核队列均走 PostgreSQL `SELECT ... FOR UPDATE SKIP LOCKED`,**不引入 Redis**(裁决:单机规模用不上,少一个依赖符合轻纪律;将来见真实瓶颈再议)。

### 3.4 词表与 alias_map 管理 【符合:不变量二、三】

- 迁移旧项目三份 YAML 词表(`structure_types` / `colors` / `alias_map`)入库,成为**带版本号的租户级词表**(见 data-model.md 的 `vocabulary` / `vocabulary_version` / `alias_map` 表)。
- 词表**版本号**写进每条标签的溯源(`vocab_version`),是"词表升级后定位需重打标签"的依据。【符合:不变量二 — 词表升级通过版本号定位受影响历史标签】
- `alias_map` 是"输出归一化层":模型输出 A、词表标准值是 B,则落库/展示时翻译为 B。归一化发生在词表层,不在数据层。
- **多语言仅留位:** 词表条目预留"概念 id → 各语言词形"结构位,本期只存中文词形,不实现翻译。【符合:不变量三 — 词表预留多语言映射位,本期不实现仅留位】

### 3.5 修正回流(sync_corrections 迁移)【符合:不变量五】

旧项目 `sync_corrections` 的数据源是"Eagle 当前标签 vs 本地 original_tags 快照"的 diff。**新平台改造:数据源 = 事件流水 + 标签修正链**,不再依赖外部 Eagle。

- diff 基准从"original_tags 快照表"改为"标签的原始值(修正链里保留的 model 原值)"。
- 变更分类沿用旧逻辑:`RENAMED`(1:1 且新值在词表内 → 建议进 alias_map)、`ADDED`(新增且不在词表 → 建议扩词表)、`REMOVED`(删除且无替代 → 记错误案例)。
- **两阶段人工闸门不变:** 扫描阶段只读、产出 review 清单;`--apply` 阶段把人工 approve 的行写入词表/alias_map,并落"配置变更"事件。冲突/成环拒绝自动写入,交人工裁决(旧逻辑保留)。
- 每次 apply 落事件流水,取代旧项目的 `applied_rules_log` SQLite 表。【符合:不变量五 — 修正回流数据源 = 事件流水 + 修正链】

### 3.6 业务事件流水 【符合:不变量五】

- 单张 `event` 表,**只增不改不删**,每条带 `tenant_id / actor / event_type / occurred_at / payload(JSONB)`。
- 覆盖行为:上传、打标完成、人工修正、选图、导出/发送、配置变更、数据导出、删除。
- **审计视图** = 事件中 `sensitive=true` 的子集(导出全库、删除、权限与配置变更),不另建审计表。
- **【Q7】写入收敛单一函数:** 所有事件写入走唯一的 `record_event(event_type, actor, subject, payload)`;`sensitive` **不由调用方手工置位**,而由函数内一张 `event_type → bool` 的集中映射推导(如 `export/delete/config_change → true`)。杜绝散落调用点漏标敏感位。`actor` 约束见 data-model §3.8(CHECK 兜底)。
- **用量计费** = 溯源记录里的 token 用量按租户/时间聚合,不另建计量系统。【符合:不变量二、五】
- 运维日志(报错/延迟)走标准 logging(stdout → 云日志),**不入**业务库。

## 4. 两个端

### 4.1 Web 管理端(内部作业)【隔断墙:UI 授权粗糙】

面向租户内部作业人员,五块功能,均只读/操作**本租户**数据:

1. **上传入库** — 批量上传,前端或后端算内容 hash,去重(见 5. 上传去重)。
2. **打标审核** — 复核队列列表、逐图查看模型标签与置信度、人工修正(走修正链)。
3. **词表管理** — 查看/编辑 structure、colors、alias_map;编辑即产生新词表版本 + 事件。
4. **事件查看** — 事件流水浏览与筛选(含审计子集)。
5. **数据导出** — 标签库 JSON/CSV + 资产打包(见 6. 导出)。

技术:后端渲染或轻量 SPA(Vue/React 皆可,属隔断墙,评审不必纠结)。**不做**租户自助开通、模板装修等管理界面。【符合:交付纪律 — 不做租户自助管理界面】

### 4.2 微信小程序使用端(一线选款)【隔断墙:UI 授权粗糙】

面向做方案的一线同事,四块功能:

1. **标签筛选** — 按 主题/配色/造型/场景 多维交叉筛选(如"配色=红金 且 造型=立柱")。

小程序**只消费**后端 API,自身无业务逻辑;账号绑定到某租户,继承租户隔离。**不做**小程序代生成、模板装修。

## 5. 资产上传与去重 【符合:不变量三】

- 上传时计算**内容 hash**(sha256)作为去重键;同租户内 hash 命中即视为重复,不重复入库(可挂为同一 asset 的别名来源)。
- `asset` 表存 `content_hash / size / mime / 上传时间 / 上传人`,以 `asset_id` 为业务主键;对象存储 key 用 `{tenant_id}/{asset_id}/...`。
- **业务逻辑一律通过 asset_id 访问,绝不依赖文件名/路径/目录**;原始文件名仅作为 `original_name` 字段留存,导出时用。【符合:不变量三】

## 6. 数据导出 【符合:不变量五】

- **标签库导出:** 按租户导出 JSON/CSV(资产 + 标签 + 溯源摘要),供离线备份或迁回本地。
- **资产打包:** 按筛选结果打包原图(zip / OSS 批量),文件名由 `suggested_filename` 或 `original_name` 生成(文件名是展示品,不承载业务)。
- 导出全库属敏感行为,落"数据导出"事件并标 `sensitive`。【符合:不变量五 — 审计视图】

## 9. 原则 vs 实现便利:冲突点(交人工裁决)

按纪律,以下是"原则严格执行会增加本期成本"的点,**不自行降级原则**,列出交裁决:

1. **单租户交付却全表带 tenant_id、全 API 带租户中间件** — 首个租户示例客户是单租户,严格隔离在本期"看不到收益"。
   *建议裁决:按原则做,不开特例(不变量一无特例条款)。成本仅为每表一列 + 一个中间件,极低。*

2. **复核队列 / 计费 是"查询/聚合"而非独立系统** — 有人可能想早点搭一个"计费模块"。
   *建议裁决:按原则,计费 = 溯源按租户聚合,不另建系统(不变量二、五)。本期连计费 UI 都不做,只保证数据可聚合。*

3. **修正回流数据源从 Eagle diff 改为事件流水 + 修正链** — 旧代码是 Eagle 专用,新平台无 Eagle,需要重写 diff 的数据来源部分(算法保留)。
   *建议裁决:必须改(不变量五明确要求)。这是迁移工作量,不是原则冲突,列此仅提示评审知悉重写范围。*

4. **对象存储选 OSS 但客户历史图在 NAS** — 一次性上云迁移有成本(2–3 万张)。见 [migration.md](./migration.md) 迁移方案。
   *非原则冲突,属交付计划,提示评审。*

5. **小程序端账号体系** — 宪法说"第一版用户名密码即可",但微信小程序自然用微信登录(openid)。
   *建议裁决:小程序用微信 openid 绑定到租户用户,Web 端用户名密码;两者都归一到"用户属于某租户"的模型,不违背隔离原则。账号体系是隔断墙,允许如此取舍。*

> 若评审对以上任一项有不同裁决,请在评审意见中注明;涉及五个不变量的任何降级需按 PRINCIPLES.md「变更纪律」书面记录并经张亮确认。
